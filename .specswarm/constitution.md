## P1. SPA only — no SSR, no server load functions

The app is a client-rendered SvelteKit SPA on `adapter-static`. The root `src/routes/+layout.ts` must keep `ssr = false` and `prerender = false`, and no SSR-only files (`+page.server.ts`, `+layout.server.ts`, `+server.ts`) may be added. All data access is client-side via supabase-js.

**Why:** ADR-0001 decides "One SvelteKit SPA (`adapter-static`, client-rendered)"; CLAUDE.md states root `+layout.ts` sets `ssr=false` and `prerender=false` with "No SSR / no server load functions". The static build is served by Caddy.

## P2. No SvelteKit server endpoints or server load files

Server-only SvelteKit files are forbidden: never add `+server.ts`, `+page.server.ts`, or `+layout.server.ts`. Server-side logic that needs secrets or privilege belongs in Supabase Edge Functions, not in SvelteKit.

**Why:** ADR-0001 + CLAUDE.md: "No SSR / no server load functions — data access is client-side via supabase-js." INV-API-003: "Operations needing secrets or privilege ... run in Edge Functions, not the client."

## P3. Svelte 5 runes mode

Runes mode is forced project-wide (`svelte.config.js`, excluding `node_modules`). All reactive state and derivations use Svelte 5 runes (`$state`, `$derived`, `$effect`, `$props`); legacy reactive syntax (`$:` labels, `export let` props) is forbidden in project components.

**Why:** CLAUDE.md: "Svelte 5 runes are forced project-wide ... Use runes." `svelte.config.js` sets `compilerOptions.runes` true for all non-node_modules files. (Compiler-enforced; no single clean regex fully captures legacy syntax, so left advisory.)

## P4. Use design tokens, not raw values, in components

Svelte components must consume the design-system tokens in `src/lib/styles/` (`var(--token)` / `.nk-*`) before any raw color, spacing, radius, font-size, or shadow value. Prefer semantic aliases (`var(--primary)`) over raw ramps (`var(--herb-500)`). Raw hex/rgb colors do not belong in components; raw values are defined only in the `src/lib/styles/**` token files.

**Why:** CLAUDE.md: "Design tokens first ... MUST be used before any custom value." Design system §4: "Use the semantic aliases, not the raw ramps."

## P5. Never render unsanitized HTML

Components must rely on Svelte's output escaping and never use unchecked `{@html}`. AI and other untrusted content is never injected as raw HTML.

**Why:** INV-SEC-010 (XSS-safe): "Rely on Svelte output escaping; never render unsanitized HTML (no unchecked `{@html}`)." CLAUDE.md: "never use unchecked `{@html}`."

## P6. Service-role key is server-only

The Supabase service-role key exists only in server / Edge-Function environments and is never shipped to or referenced from client code under `src/`. The anon (publishable) key is public; security derives from RLS + Auth, not from key secrecy.

**Why:** INV-SEC-011: "The service-role key exists only in server / Edge-Function environments." INV-API-002: "The service-role key is never shipped to clients."

## P7. RLS enabled, default-deny, before any table is exposed

Every table holding user data must have Row-Level Security enabled with explicit policies before it is exposed to clients. Tables grant no access by default; policies grant access explicitly. RLS is the sole authorization boundary — the client is never trusted for authorization.

**Why:** INV-DB-011: "Every table holding user data has RLS enabled with explicit policies before it is exposed." INV-SEC-006 (default deny); INV-API-001: "the client is never trusted for authorization."

## P8. UUID primary keys, no auto-increment

Primary keys are UUIDs (client-generatable, non-enumerable). Auto-increment / serial keys are forbidden, and IDs encode no meaning (treat as opaque).

**Why:** INV-DB-001: "Primary keys are UUIDs (client-generatable, non-enumerable); no auto-increment." INV-DB-005: "IDs encode no meaning."

## P9. Timestamps are timestamptz in UTC

All timestamp columns use Postgres `timestamptz`, stored and compared in UTC. Bare `timestamp` / `timestamp without time zone` is forbidden. Display converts to the user's configured timezone.

**Why:** INV-DB-002 / INV-TZ-001: "Timestamps use Postgres `timestamptz`, stored and compared in UTC." INV-TZ-002: display in user timezone.

## P10. Injection-safe data access in Edge Functions

Edge Functions access data via PostgREST / parameterized queries; no string-concatenated SQL. All access remains governed by RLS, and inputs are validated before persistence.

**Why:** INV-SEC-009: "Data access uses PostgREST/parameterized queries; no string-built SQL in Edge Functions." INV-API-004: validation before persistence. (Real rule, but reliable regex detection of dynamic SQL is impractical — left advisory.)

---

## P11. AI output is untrusted and data minimized

AI output is treated as untrusted input and validated before persistence or rendering. Only data needed for a feature is sent to cloud AI providers — never tokens or credentials, with PII minimized — and AI use is disclosed.

**Why:** INV-PRI-006: "AI output is treated as untrusted input and validated before persistence." INV-PRI-003 (data minimization); INV-PRI-004 (AI use disclosed). Backs P5; not itself a single-regex check.

---

## P12. Every test must assert; server-only code is isolated

The vitest suite runs `expect.requireAssertions` — every test must make at least one assertion. The two-project setup keeps server-only code under `src/lib/server/**` (excluded from the browser/client project); client component tests live in `*.svelte.{test,spec}.{js,ts}`.

**Why:** CLAUDE.md: "`expect.requireAssertions` is on: every test must make an assertion" and "`src/lib/server/**` is excluded from the client project — put server-only code there."

## P13. No clinical labels in user-facing UI

The UI never surfaces "ADHD" or other clinical terminology. ADHD accommodations live in the UX, framed as personal preference, never as user-facing labels. Shame-free voice is non-configurable.

**Why:** REQ-CFG-006: "The system shall never surface 'ADHD' terminology or other clinical labels in user-facing UI." Design system §1: "Never name ADHD or clinical concepts in the UI."

## P14. Append-only records are never overwritten

`MealLog` and `PortionEvent` rows are append-only and are never overwritten by last-write-wins. Prepped-meal portion changes are recorded as append-only `PortionEvent` rows; remaining portions are derived from the ledger, never blind-overwritten.

**Why:** INV-CC-004: "`MealLog` and `PortionEvent` are append-only and are never overwritten by LWW." INV-CC-006 / INV-INV-004 (portion ledger non-negative, derived not overwritten).

---

## P15. Online-first; server authoritative; no offline write queue

Supabase Postgres is the single source of truth; client caches are a disposable read cache. Optimistic updates must reconcile against the server response and roll back on rejection. There is no offline write queue and no conflict-resolution engine; Realtime is best-effort and correctness never depends on receiving an event.

**Why:** ADR-0002: "Supabase Postgres is always authoritative ... no offline write queue and no conflict-resolution engine." INV-CC-001/002/005.
